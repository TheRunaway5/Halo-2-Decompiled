## Original request and timing

Retail image SHA-256 is `03215919bb7163259257d361f4c7bf802a7ab12aa85e2689436369b5c427935d`; TU1.1 is `aaea4c9c58ac02cf5f9cc97a16d688318c59b652e92301078e2547a2a5ea5377`.

Ordinary recharge is retail `D5DE0`, TU1.1 `D73E0`, one stack full-object datum, `RET 4`. Its [TU1.1 instructions](../analysis/damage-shields-goal-20261011/shield-break-recharge-live/instructions/tu11-000d73e0.asm) show the ordinary branch:

1. A living object (`body-depleted bit2` clear), positive maximum shield `body+E8`, and normalized shield `body+F0` below the selected maximum enter the recharge/stun branch. Overshield charge/drain are separate earlier branches.
2. Signed shield stun `body+104` must equal **zero**. Nonzero values, including negative values, take the stun branch. Except when the original pause owner says paused or the value is `7FFF`, that branch decrements the signed WORD, clears recharging bit9, and marks update mask80. Stun1 reaches0 this tick; recharge begins on a later invocation.
3. Recharge increment is original clock `[*518444+4]` times damage-info `+D0`, or actor bounds `+6C` when that actual owner is present; units additionally apply `1ED0B0(selector3,team body+138)`. This value does **not** gate the request.
4. If depleted bit3 was set, `D78E3` clears it and calls real `BB6E0(object,NONE,2,0)` before the effect request.
5. If prior recharging bit9 was clear, `D791A` calls `D7CD0(object,&owner)` and `D7939` calls `1781F0`. At that call the old shield vitality is still present. The authored tag is damage-info `+B8`; EDX=object, EBX=&the actual owner, XMM0.low=0, stack arguments `(tag,0,0,0)`, `RET 10h` at `1781F0`. `D7CD0` supplies owner object/player/team from `body+C8/C4/C2`. The source writes ten meaningful owner bytes; two trailing padding bytes were not read by the stopped transition fixture and are not authenticated there.
6. Only after the request returns does `D794A` set recharging bit9, add the increment, store `F0`, and test strict `>` maximum. Overshoot clamps and clears charging/damaged bits; exact equality leaves charging set until a later ordinary call. Zero rate still requests once and sets charging; overshoot rate requests before its same-call clamp.

These are the [reference C navigation](../tools/reference/halo2-decompiled/src/damage.cpp) and unchanged machine instructions, not an interpretation of a desired visual result. Body recharge has its own later branch.

## Attachment and event creation are separate owners

Retail [176780](../analysis/damage-shields-goal-20261011/shield-break-recharge-live/instructions/retail-00176780.asm), TU1.1 [1781F0](../analysis/damage-shields-goal-20261011/shield-break-recharge-live/instructions/tu11-001781f0.asm), sets parameters flags `|5` (attached and forced request), obtains the actual object bounding center (`B9DD0` /`BACC0`) and two seed markers (`176330` /`177DA0`), copies the supplied owner, then calls the real allocation/attachment constructor `175FA0` /`177A10`. Forced request still has genuine allocation failure; it is not a successful handle supplied by this research.

The [constructor](../analysis/damage-shields-goal-20261011/shield-break-recharge-live/instructions/retail-00175fa0.asm) retains actual object/first-person attachment identity and calls [178360 /179DD0](../analysis/damage-shields-goal-20261011/shield-break-recharge-live/instructions/retail-00178360.asm). That owner resolves every authored location: explicit seed marker, actual object marker query `B8D30` (TU1.1 `B9C20`, up to16 records), then actual first-person markers when their owner is valid. Only its literal root fallback applies; arbitrary unresolved names are not replaced by root. Result locations retain node index/matrix and first-person bit, and later updates compose current node transforms. See the [frozen source](../analysis/damage-shields-goal-20261011/shield-break-recharge-live/source-snapshot/tools/reference/halo2-decompiled/src/unknown_175bd0.cpp).

Creation selects event0 and calls original `179850` with initial dt **1.0** when definition bit1 is set and effect flags1/9 are clear, otherwise **0.0**. Thus these depleted/damaged definitions request immediate source advancement through their short event; recharge definitions begin with0. Ordinary event duration alone is not particle lifetime. `1792B0` splits delay/duration, starts actual parts, advances particle systems, progresses/skips/loops and retires only through original owners. Existing [SourceEffectEvent](../include/halo2/source_effect_event.hpp) preserves the numeric clock boundary, but does not itself construct attachments or allocate a real original effect.

## Current MAIN/native joins and minimum deliverable

The [frozen native sources](../analysis/damage-shields-goal-20261011/shield-break-recharge-live/source-snapshot.json) distinguish code inspection from execution. `Simulation::damage` calls `apply_unit_damage` and currently discards its ordered `result.effects()`; `Simulation::step` calls scalar recharge without an effect result. The host unit adapter already determines damage/depletion requests. A reusable ordinary-update result can add the recharge attempt at the exact **pre-write transition**, carrying actual effect datum, full object lifetime handle, actual owning damage-owner fields, tick, zero A/B scales and attachment intent. The shared simulation should queue these events once in source order; the active renderer/audio owner consumes the queue. Do not derive requests afterward solely from shield increasing, final charging state, or shield reaching zero. Those tests miss zero/overshoot rate and repeat suppression.

`src/main.cpp` currently submits debug/body/FP geometry and screen effects; it has no `NativeWorldEffects` owner. `multiplayer_runtime.cpp` already constructs `NativeWorldEffects`, advances it at game ticks, and draws through its per-view effect path, but that alone does not connect shield requests. Its current API stores one immutable `WorldEffectFrame`, supports static scenery attachment and world/impact directions, rejects nonzero particle coordinate systems, cannot resolve arbitrary posed body markers, loads particle sprites/materials as prt3 only, and permits vertex classes7/8. `load_particle_material` explicitly requests group prt3. The separate particle creation/render-input kernels already distinguish world/nonworld coordinates numerically; they still need actual current/previous attachment frame and first-person/view inputs from the accepted pose owner. A generic root spawn cannot supply that ownership.

The smallest **complete reusable presentation path** therefore needs: (1) the ordered request queue above in the actual shared update; (2) an attached-object frame resolver keyed by full handle and authored location, receiving the accepted model/variant/nodes and per-view first-person owner; (3) original creation initial advancement and subsequent game-tick event/particle scheduling with actual RNG owners; (4) PRTM property/mesh/material dispatch and class9 prt3 support; (5) complete light/particle submission through the existing scene transparency and view schedule. The actual retail `137BD0` discriminates prt3 and PRTM providers; converting PRTM to a billboard or substituting a glowing shell is unsupported. Break/recharge effects are distinct from the body shield-hit shader overlay, so wiring only that overlay does not fulfill these graphs.

This handoff establishes original requests and raw authored requirements. It claims no live collision-to-visible break/recharge completion, no successful original allocation/admission, no final material/lighting/topology parity, no network event transport, and no rendered Xbox comparison. Further PRTM consumer evidence follows as an addendum rather than being inferred from tag names.

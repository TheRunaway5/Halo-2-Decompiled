# Smallest ordinary character GPU skin seam

2026-10-22. Read-only inspection of current canonical source; no builds, probes, game launches or session revival. The user authorized implementation by the parent agent. This note proposes a boundary, not GPU-output equivalence or a measured gain.

**The smallest candidate is compute skinning into the current expanded `Vertex` ABI, retaining the existing material/PRT/normalization graphics path. A full raw-original shader bridge is not inherently required.** CPU shader selection uses section/part metadata, not posed positions. The difficult part is removing actual CPU skin calls while preserving earlier geometry consumers and the renderer's pose-dependent storage identity.

## What can stay metadata-only, and what needs real posed geometry

The CPU skin changes exactly `position`, `normal`, `tangent`, `binormal` ([kernel:42](/home/eric/Developer/Halo-2-Decompiled/src/rendering/models/model_skin_vertices.hpp:42)). Color, incident, UV/lightmap, PRT cluster/weights, source-local position, alpha/stipple and source provenance remain copied unchanged. Shader-part selection, material-offset application and grouping can operate on those unchanged records plus an explicit skin mapping.

Current posed-data consumers cannot receive local-space placeholders:

- **pStencil lightmap casters:** [runtime:3970](/home/eric/Developer/Halo-2-Decompiled/src/gameplay/multiplayer/multiplayer_runtime.cpp:3970) copies actual body triangles when pStencil and valid incident/light samples require them. [Frame::add_lightmap:73](/home/eric/Developer/Halo-2-Decompiled/src/pstencil/frame.cpp:73) reads each posed triangle's positions and builds CPU volume geometry. A first GPU-only admission must fall back when this actual caster is required, or separately implement/validate a GPU caster bridge. It cannot drop shadows. Renderer fallback caster generation also reads vertices at [5872](/home/eric/Developer/Halo-2-Decompiled/src/rendering/renderer/renderer.cpp:5872).
- **Shields:** [append_shields:4322](/home/eric/Developer/Halo-2-Decompiled/src/gameplay/multiplayer/multiplayer_runtime.cpp:4322) itself clones/selects records and adjusts material IDs; its selection does not require posed arithmetic. But the resulting overlay must consume the same posed geometry, and `shield_layer_observer` receives actual full vertices. Either share the computed result into each overlay's exact output mapping, or retain the CPU path for visible shield consumers initially.
- **Observers/diagnostics:** `animation_observer` gets full body/weapon banks at [5780](/home/eric/Developer/Halo-2-Decompiled/src/gameplay/multiplayer/multiplayer_runtime.cpp:5780); `unit_source_draw_observer` gets actual submitted vertices at [5601](/home/eric/Developer/Halo-2-Decompiled/src/gameplay/multiplayer/multiplayer_runtime.cpp:5601). Frame finite-position validation, byte-comparison/upload diagnostics and capture paths also inspect CPU bytes ([renderer:4310](/home/eric/Developer/Halo-2-Decompiled/src/rendering/renderer/renderer.cpp:4310), [5898](/home/eric/Developer/Halo-2-Decompiled/src/rendering/renderer/renderer.cpp:5898)). Use an explicit CPU fallback or an independently synchronized validation/readback path; do not feed observers fabricated posed data or suppress them.
- **Pose/gameplay ownership:** attachments/IK/interpolation need current WORLD nodes, not necessarily every skinned mesh vertex. Keep those completed CPU node banks and all source callbacks. Ordinary base presentation is the proposed offload, not animation/physics/source arena execution.

**Important work-elimination gate:** the body loop creates default CPU skins at [5762](/home/eric/Developer/Halo-2-Decompiled/src/gameplay/multiplayer/multiplayer_runtime.cpp:5762) and selected skins at [5774](/home/eric/Developer/Halo-2-Decompiled/src/gameplay/multiplayer/multiplayer_runtime.cpp:5774), before `append_unit_base` decides whether ordinary geometry was already supplied. Adding a GPU packet late can leave those complete CPU skins running. Decide admission before skin creation using the full actual consumer set, preserve the CPU fallback, and count eliminated CPU skin calls in the ordinary runtime. GPU dispatch plus unchanged CPU skinning is not the requested optimization.

## Proposed minimal compute contract

Retain exact CPU palette composition initially. Offload only the last per-vertex blend/transform kernel: descending influences, separately rounded multiplication/addition, `(x+y)+z`, translation only for position, zero-influence records untouched. Keep normal/tangent/binormal unnormalized here. Existing [source input:13](/home/eric/Developer/Halo-2-Decompiled/shaders/source_vertex_inputs.glsl:13) applies the separately proved skinned-normal operation for specific programs, and [CPU input qualification:13](/home/eric/Developer/Halo-2-Decompiled/src/rendering/models/source_cpu_skin_inputs.cpp:13) distinguishes reflection and shield-local-position contracts. PRT streams and per-owner constant banks ([renderer:5431](/home/eric/Developer/Halo-2-Decompiled/src/rendering/renderer/renderer.cpp:5431)) remain in the existing graphics path. Compute must not normalize twice, transform incident/color/PRT inputs, or overwrite `source_local_position`.

Required packet/storage facts:

1. **Stable source mapping:** [RenderModel:28](/home/eric/Developer/Halo-2-Decompiled/include/halo2/model.hpp:28) stores expanded vertices, parallel `SkinBinding` entries and `VertexOrigin` records. [Vertex:115](/home/eric/Developer/Halo-2-Decompiled/include/halo2/cache.hpp:115) retains section/part but **not** its expanded ordinal or original vertex index. The current section/filter copies discard that parallel index. Carry exact expanded indices or paired bindings through selection; position matching cannot recover influence identity. Preserve repeated sections and repeated vertices in original encounter order.
2. **Complete destination mapping:** grouping can concatenate nonadjacent source runs. Associate every selected expanded input with its final GPU output index, or use a separately retained output buffer/range bound by the draw. The existing `ModelView`/`ModelObjectDraw` interfaces expose only CPU spans; a new explicit packet/stream owner is needed. It must pin immutable model/LOD, complete owner generation, current palette, selected ordered indices, material metadata and output ranges through GPU completion.
3. **No false deduplication:** [FrameVertexUploadPlan:23](/home/eric/Developer/Halo-2-Decompiled/src/rendering/renderer/frame_vertex_upload_plan.hpp:23) shares equal full CPU bytes. Posed data currently distinguishes different poses implicitly. Equal **local** records can belong to different palettes/owners; the current DrawKey contains neither. Extend sharing identity with complete pose/source identity, or exclude these GPU jobs from current byte sharing. Two writes to one deduplicated destination are not a valid two-pose result.
4. **GPU ABI and synchronization:** `debug_buffer` currently has vertex-only usage at [1213](/home/eric/Developer/Halo-2-Decompiled/src/rendering/renderer/renderer.cpp:1213) and [5416](/home/eric/Developer/Halo-2-Decompiled/src/rendering/renderer/renderer.cpp:5416). A compute destination needs storage usage, validated byte offsets/stride and device range/workgroup limits. Do not assume a GLSL `std430` struct with `vec3` has the C++ `Vertex` layout; use qualified offsets/word storage or an independently verified layout. The selected queue already requires graphics+compute at [1020](/home/eric/Developer/Halo-2-Decompiled/src/rendering/renderer/renderer.cpp:1020). Record dispatch after protected upload and before graphics consumers, with compute shader write → vertex input attribute read synchronization, then retain the existing frame-fence lifetime. [Khronos compute/graphics examples](https://docs.vulkan.org/guide/latest/synchronization_examples.html), [vertex-buffer access contract](https://docs.vulkan.org/refpages/latest/refpages/source/VkAccessFlagBits.html).

This is a compute-after-packing design option, not a mandate to add per-frame readback. A full raw-original base bridge can instead retain packed original resources and execute original class-specific programs, but it also needs ordinary material/PRT/pass integration. The existing expanded stream offers a smaller first arithmetic seam because those material adaptations are already present.

## Critical admission/regressions

- Compare compute output against the unchanged CPU kernel for all four posed attributes **and every untouched record byte**, actual authored models/LODs, compounds, 0–4 influences, zero/signed-zero/subnormal cases and malformed-bank fallback. Keep exact influence order and source fault checks. Require nonzero GPU jobs and actual CPU-skin elimination; a fallback-only test proves no integration.

None currently proves a new ordinary compute path.
- Run matched full renderer output/draw/pass comparisons with the actual target binary and 1–4 views after direct GPU readback proof. Include body/base/environment/overlay/shield/fog/pStencil behavior. CPU component equality, a dispatch counter or an approximate screenshot is not full visual admission.

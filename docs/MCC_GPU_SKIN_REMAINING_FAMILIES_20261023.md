## Next bounded experiment if GPU dispatch has little net gain

First measure the actual remaining final-kernel work and its admission reasons in the normal pinned 1p/4p workload; body/first-person phase timers include much more than deformation. Palette construction, checked source execution, shader selection and copies remain CPU after GPU migration. Existing historic skin percentages do not bound today's savings.

The smallest additional GPU family is source mode0 looking-down body, followed by real loose-weapon source units. Neither should land until the current framebuffer mismatch is resolved. If dispatch/upload overhead cancels kernel savings, a falsifiable alternative is **one CPU presentation-worker job running the unchanged SIMD final kernel** over substantial already-owned local/palette/binding spans. Restrict initially to the same normal-success numeric/host domain: all source/palette/node/IK construction remains ordered on its owner, the skipped caller kernel has no new sticky effects because PE is already set, and the worker receives identical controls and disjoint output storage. Allocate/copy and fully validate inputs on the owner before dispatch, keep mutable pose-cache maps/source memory/Vulkan calls off the worker, and join before the first posed shield/observer/append consumer. Restore worker fenv/errno; do not synthesize owner flags. Diagnostic/unsupported cases stay on the old CPU path. This avoids new GPU numerics/packing costs, but scheduling, overlap, failure order and exact result/effect proof are still required; it is an experiment, not established speedup. The existing copy worker does byte copies only and does not already implement this skin-job contract.

For the corpse-specific repeated full skin, reuse is a smaller experiment than another worker/dispatch: same full owner/model/node bytes, frame-local lifetime, complete source/pose identity and strict recorded-effect containment can permit compatible view hits. It must prove zero changes to the original cold calls, selected geometry, faults, observers and sticky/x87/errno state. Do not generalize across changing ragdoll nodes, model generations or the existing selected cache's temporary/LOD model identities.

## Reconcile earlier MCC/offload claims

`docs/MCC_PERFORMANCE_OFFLOAD_20261022.md` is pinned historical source evidence. Its “ordinary unit CPU skins” and proposed raw-base bridge describe that earlier code, not today's compute packet implementation. The present compute route deforms the existing packed attributes under a restricted exact domain; it does not establish an arbitrary raw-original-VP bridge or all-model GPU parity. Likewise the new byte-copy worker does not establish parallel source callbacks or command recording.

The retained MCC binary evidence still supports native direct field loads, D3D11 deferred-context/command-list machinery, redundant binding suppression, an indexed instancing branch and native buffer allocation/rotation. It does **not** establish live worker count, actual ordinary skin-family placement, persistent residency cadence, per-pass cost or the causal share of the reported 4K120 advantage. Microsoft still explicitly permits deferred-list merging while requiring eventual immediate-context execution for GPU playback ([ExecuteCommandList](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-executecommandlist)); shared MCC field offsets alone do not establish receiver instance or live concurrency. Vulkan likewise requires explicit command-pool ownership/synchronization for any future command worker ([command buffers](https://docs.vulkan.org/spec/latest/chapters/cmdbuffers.html#commandbuffers-pools)). None of these API mechanisms certifies matched MCC/port FPS.

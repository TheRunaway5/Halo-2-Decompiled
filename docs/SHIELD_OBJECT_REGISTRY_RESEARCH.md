# Authoritative object lifetime handoff for the shield collector

Research snapshot: 2026-10-11. The next implementable owner is a persistent object registry inside the authoritative simulation, supplied at allocation/construction time and updated where the simulation changes an owner. The existing `SourceObjectRegistrationJournal` already owns the recovered registration prefix and independent spatial pools. Current render-scene synchronization does not provide the missing event history. One prerequisite is concrete: scenario objects and multiplayer objects currently allocate from **different identity pools**, so their handles cannot be inserted together into one journal. This note changes no implementation. It continues [the live-producer report](SHIELD_LIVE_PRODUCER_RESEARCH.md) and narrows [the existing registration seam](SOURCE_OBJECT_LIVE_REGISTRATION_SEAM.md) to current call sites.

**Snapshot chronology:** the sections through the original evidence gates retain the pre-integration snapshot. The final section below verifies the original shared pool and records the parent's subsequent `NativeObjectLifetimes` integration. The earlier separate-pool description is the defect at that earlier snapshot, not a claim about the later implementation.

The original authority is [retail default.xbe](../assets/disc/default.xbe), SHA-256 `03215919bb7163259257d361f4c7bf802a7ab12aa85e2689436369b5c427935d`. The retained [instruction/native manifest](../analysis/damage-shields-goal-20261011/overlay-pass/registration/source-evidence.json) records that hash, all 20 original routine bodies and 38 concurrent native files. [The cold-input index](../analysis/damage-shields-goal-20261011/overlay-pass/registration/cold-input-index.json) hashes the six earlier independent observation reports and indexes their actual Lockout fields. ## Identity and ownership must precede collection

`SceneObjects::place` finds a free scenario slot, increments that slot's generation and constructs `(generation << 16) | (slot + 1)`. `MultiplayerMatch` separately owns `DatumPool("object", 0x800, 12)`, whose allocation returns `(salt << 16) | slot`. The former begins at low16 index1; the latter begins at index0 and can allocate index1 next. Different salts do not solve this: `SourceObjectRegistrationJournal::birth` correctly rejects duplicate low16 identities as well as duplicate full handles or retained pool ranks. Original low16 visitation stamps also require one coherent index namespace. [Scene allocation](../src/scene.cpp#L130), [match storage](../include/halo2/multiplayer.hpp#L293), [datum allocation](../src/datum_pool.cpp#L36), [journal checks](../src/source_object_spatial_pool.cpp#L140).

Use one authoritative object allocator and rank namespace for these categories before claiming a complete shared registry. It must exist before scenario construction: `MultiplayerMatch::simulation_` is currently declared before its object pool, and `Simulation` constructs `scene_` in its initializer list; the match only installs allocation/release callbacks afterward. Installing a renderer observer or replaying the surviving scene in the match constructor misses earlier construction and destruction. A separately labelled scenario-only journal is possible while this change is staged, but it cannot establish joint unit/prop admission or original cross-category list order. A synthetic rank, rewritten datum or category offset is not evidence of original allocation chronology. [Declaration order](../include/halo2/multiplayer.hpp#L293), [simulation construction](../src/simulation.cpp#L286), [late callbacks](../src/multiplayer.cpp#L244).

`SourceObjectInitialization` contains a useful model/RNG construction ledger and `creation_sequence`, but there is no production `SourceObjectInitialization::create` caller in this snapshot. It is not an existing authoritative global birth ledger. Likewise, `SourceSceneryScene::birth_query_capture` observes birth during later scene synchronization, after it has found a current placement in a vector. Preserve it for its cached-query purpose; do not use it to reconstruct same-tick lifecycle ordering. [Model ledger](../src/object_initialization.cpp#L96), [scenery capture](../src/source_scenery_scene.cpp#L216).

## Minimum persistent integration contract

1. Place one lifetime/allocator owner before `SceneObjects` construction and share it with match unit, weapon and grenade allocations. Keep reservation, constructor completion and registration as distinct events. Provide a pre-construction observer/typed construction callback, not a post-construction enumeration. Record actual global ordinals and native successful slot rank; do not claim recovered retail successful-slot chronology from the native policy alone.
2. Supply a validated **unregistered** construction packet after its actual node/bounds/classification producers. Start with the bounded cold authored branch whose inputs are already recovered; separately recover/import the missing live unit, held/dropped item and grenade fields above. Preserve initial activation versus later seeded/supplied/NULL registration. The journal owns the two spatial banks, old location, registered bits and retained primitive; the caller owns admitted backend/activation outcomes.
3. Add explicit topology mutation to the lifetime owner/journal before held children can join a shared registry. Original `B8EE0` deactivates and unregisters the child (`B8F0A..B8F1C`); `B93B0` can unregister again after its gated branch, writes parent, prepends sibling/child links, sets header80 and resets location (`B950A..B9548`). Current journal has no operation updating these links after birth. Drop/release must use their actual detach/transform/register services; unregistering a child does not itself maintain the parent list. [B8EE0](../analysis/damage-shields-goal-20261011/overlay-pass/registration/000b8ee0-retail.asm), [B93B0](../analysis/damage-shields-goal-20261011/overlay-pass/registration/000b93b0-retail.asm), [current journal API](../include/halo2/source_object_spatial_pool.hpp#L75).
4. Emit `primitive_update` only for admitted classification changes; preserve links/order. Emit `bound_refresh` at actual bounds updates, retaining **both** rendering sphere and selected primitive. Original BDEF0 updates query/dynamic fields, compares the retained primitive with source squared threshold `.010000000707805157`, and only then unregisters/reinserts changed registered owners. Explicit B7430 transform registration is a separate supplied-location operation. A per-frame remove/reinsert of every rendered object changes list order. [BDEF0](../analysis/damage-shields-goal-20261011/overlay-pass/registration/000bdef0-retail.asm), [B7430](../analysis/damage-shields-goal-20261011/overlay-pass/registration/000b7430-retail.asm), [journal operations](../src/source_object_spatial_pool.cpp#L181).
5. Destruction must perform actual detach/deactivation, root unregister, attachment callbacks and child recursion before free. `B8460` establishes that order and ends with `BC300`; journal `free` rejects still-registered owners and nonempty child heads. Preserve corpses, unbound netgame items and unequipped inventory items until their actual destruction event. Add an explicit BSP deactivate/epoch lifecycle before claiming BSP-switch coverage; current journal has no whole-epoch reset method. [B8460](../analysis/damage-shields-goal-20261011/overlay-pass/registration/000b8460-retail.asm), [B6C50](../analysis/damage-shields-goal-20261011/overlay-pass/registration/000b6c50-retail.asm).
6. Copy/restore allocator, journal, ordinal, hierarchy, registry epoch and associated cache history with the authoritative `Simulation::SavedState`. `SceneObjects::restore` presently restores only its own arrays/functions/context. Replication must carry authoritative event order or a complete validated registry checkpoint; a current player/grenade/prop snapshot cannot reconstruct missed same-tick register/relink/free events. [Checkpoint](../src/simulation.cpp#L98), [scene restore](../src/scene.cpp#L119).

After registration the existing journal returns `activation_services_required`. That remains a real boundary: `BEF30` attachment lights, `B6D60` interested-cluster activation/machine portal overrides, physical activation/authority and old-NONE backend callbacks are not proved by the registration prefix. Current camera visibility is not the interested-cluster bitmap. The registry may feed only the categories/branches whose packet and event services are supplied; it must report missing owners instead of using rendering presence as registration. [Existing exact boundary](SOURCE_OBJECT_LIVE_REGISTRATION_SEAM.md#remaining-activation-and-backend-services).

Evidence gates for this increment are: same-tick create/destroy/recreate and allocation rollback preserve ordinals; joint scenario/unit/weapon/projectile low16 identities are unambiguous; hidden retained owners remain present; parent/child detach and recursive free preserve actual links; unchanged bound refresh preserves list order while changed refresh uses the retained primitive threshold; an invalid supplied location differs from NULL fallback; full checkpoint restore reproduces complete raw spatial-bank state. These are registry gates. The parent has separately validated the transparent queue/renderer increment (117 original streams/215,807 words, 111 FP traces and bounded actual shield RGB inspections); those results do not supply the lifetime producer inputs identified here.

Reservation, completed construction, registration and storage release remain distinct source operations:

1. Retail `BC280`/TU1.1 `BD170` first reserve a header (`16B840`/actual `16D2C0`), then ask the separate object-body heap for storage. Successful allocation stores the requested signed-short extent in header `+6` and zeroes exactly that body extent. It does not complete the type constructor or register the object. A body-allocation failure releases the already reserved header (`16BA40`/actual `16D4C0`) before returning `NONE`. [Retail allocation](../analysis/damage-shields-goal-20261011/overlay-pass/registration/shared-pool-proof/000bc280-retail.asm), [TU1.1 allocation](../analysis/damage-shields-goal-20261011/overlay-pass/registration/shared-pool-proof/000bd170-tu11.asm).
2. The generic constructor then initializes and extends the body. In actual TU1.1 `B8A30`, extension failure reaches `BD1F0` at `B9278`; a failed type constructor first calls `10CD80` at `B926E`, then releases storage at the same edge. The earlier unchanged-original report executes **905** actual raw `BD170(464)` pressure attempts until real finite-heap failure. After freeing one raw pressure body, a fresh generic call gets `E5FB0389`, fails its third `BD270` extension (`124`, size `60`) and executes `BD1F0`, returning `NONE`. ## Ordered hierarchy mutations

The native [registration journal contract](../include/halo2/source_object_spatial_pool.hpp) and [implementation](../src/source_object_spatial_pool.cpp) now carry the literal parent-node byte at object `+18`, with full parent `+14`, child-head `+10` and sibling `+C`. Explicit monotonic `attach_link` and `detach_link` events copy with the entire journal, including its spatial pools and earlier event order. These are native integration events; their ordinals are not an original event format or recovered successful-construction chronology.

Attachment is deliberately the **post-admission, post-deactivation/unregister/backend-removal topology slice**, retail `B950A..B9548` / TU1.1 `BA3FA..BA438`. [Pinned TU1.1 attachment instructions](../analysis/multiplayer/integration/inventory-source/weapon-attachment/instructions/000ba2a0.asm).

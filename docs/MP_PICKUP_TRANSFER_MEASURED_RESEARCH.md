# Original TU1.1 held-input and retained-item transfer measurement

Research date: 2026-10-08. This separate, read-only extension measures the shortest executed ordinary pickup chain on the already frozen allocated/equipped Spartan fixture. It preserves production, [FBFA0](MP_ITEM_POINT_RESEARCH.md), and every earlier oracle/report. The original hardware/control, animation admission, inventory ownership, world removal and marker attachment instructions execute; no successful admission, carry, collision or pose result is supplied. The explicitly nearby unit root and original fixture's storage/residency/scheduling boundaries remain inputs. [Measurement tool](../tools/oracle_mp_pickup_transfer_measured_1_1.py), [frozen attachment environment](MP_WEAPON_ATTACHMENT_RESEARCH.md).

The useful integration slice is **source-produced control/request bytes → repeated admission → full-datum ownership/slot transfer → source selection/hand attachment**. It is now represented as measured input/output states and an ordered store stream. It does not establish complete live placement, motion, world registration, normal item settling, engine scheduling or Xbox reciprocal parity. [Report](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/report.json).

## Ordinary action, admission and slot transfer

Source hardware polling and actual profile/action generation precede the player fragment. In the primary BR case, private action `u16 +1C` enters `150F00` as **0007** (held, threshold and pressed) with sequence 1 / slots `[0,FF]`. The secondary SMG case enters as **0070** with the same sequence/slots. Primary threshold first tries `1533E0` and then `153090(primary=1)`; secondary threshold calls `153090(primary=0)`. The selected candidate is actual allocated datum **00020003**, not a definition replacement. [Exact measured control/candidate inputs](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/report.json), [150F00 source](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/00150f00.asm).

`153090` validates candidate kind 1 or 7, original datum admission through `BBD10`, actual weapon type, unowned item `+154=FFFFFFFF`, and `CEC00`. For BR, actual four admission bytes are **01 00 01 00**; for secondary SMG they are **00 01 00 00**. The selector chooses mode **3** or **5**, respectively. Actual `139FF0` takes the ordinary action path, building a zero-filled 32-byte request with `u32 +0=20`, full item datum `u32 +4=00020003`, and mode `u16 +8`. `E7F30` dispatches that request to `EA660`. [153090 admission/request writes](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/00153090.asm), [literal request bytes](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/report.json).

`EA660` rechecks unowned item state and `CEC00`, validates the mode's specific admission byte, then invokes `E7FF0` to cancel types **8, 18, 0, 10, 27, 22**, in that order. Only afterward does it call `CE510`. The unchanged carry path checks original item/object flags, `CEAF0` graph capability and mode-specific hand constraints, repeats `CEC00`, and calls `CEA70`. This routine scans the four full-datum slots at `unit+218..+224` in ascending order for `FFFFFFFF`; it returns **slot 1** in both ordinary cases. Full-inventory `FFFF`, mounted/forbidden-definition gates, different modes and replacement choices remain source-listed but unexecuted by these two cases. [EA660](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/000ea660.asm), [CEAF0](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/000ceaf0.asm), [CEA70](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/000cea70.asm).

`CFED0` receives `ECX=00020003`, `DX=1`, `EAX=FFFFFFFF`, and stack unit **00010001**. Its measured order is:

1. `FB120(item,new-owner=unit)` assigns ownership and runs original activation/scale/bounds/location callbacks.
2. `FB3F0(item)` holsters/deactivates the item and removes its world registry membership.
3. `CFF0F` stores the full item datum at `unit+21C`.
4. `CFF16` writes zero to that slot's ready timestamp at `unit+22C`.
5. `CFE60` advances both unit sequence words `+210/+214` from 1 to 2.

No new weapon allocation or replacement object is performed during these ordinary transfers. The initial SMG remains **00010002**; the target remains **00020003**; object pool high-water/count stay unchanged. The originating map row and its runtime datum remain intact. [CFED0 stores](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/000cfed0.asm), [measured pool/row/slot states](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/report.json).

`CFE60` executes only when options byte `+0C` differs from 4. Its arithmetic reads the low sequence byte, increments it, masks with `0F`, and writes the two 16-bit words at `CFE9B/CFEA2`. The subsequent network-dirty callback is skipped because the inherited source fixture has `unit+D4=FFFFFFFF`. The compare against `FFFF` after the low-nibble mask is retained in the original listing; it is not grounds for inventing a reachable reset case. [Sequence owner instructions](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/000cfe60.asm).

## Ownership, registry membership and parent attachment are separate

`FB120` stores target item flags `+12C` **00→05** at `FB184` and owner `+154` **FFFFFFFF→00010001** at `FB18F`. Original `FB360` adds the player-owned bit, producing **0D**. **The item still has its actual world registry membership at FB120 return.** BR remains in cluster9, secondary SMG in cluster15. The nested `B96A0` during source bounds/location update is not a permanent world-removal result: the owning callback completes with the source target registered. [FB120 and FB360](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/000fb120.asm), [exact `registry_before/registry_after` chains](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/report.json).

`FB3F0` next changes item flags **0D→0F** at `FB421`, updates object activation flags, and executes the original unregister path. Its return has **empty registry chains** before `CFED0` stores the inventory slot. The report pins the ordered, unsorted original chain entries and raw 32-byte registry records before and after `FB120`, `FB3F0`, `FB560`, `B96A0` and relevant allocator removals. Do not remove the map row datum, delete the weapon object, or equate owner assignment with final unregister. [FB3F0](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/000fb3f0.asm), [B96A0](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/000b96a0.asm), [measured chain checks](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/audit.json).

After slot storage and sequence advance, `CE510` writes desired primary `+216=1` at `CE858` for mode 3, or desired secondary `+217=1` at `CE875` for mode 5. It emits actual selection type **8** or **18**, respectively. Original `E9D50→D1D20→FB560` then performs the previously frozen marker attachment. The BR uses actual right-hand marker **0A000798**, parent node **20**; the second SMG uses left-hand marker **09000100**, node **19**. Child marker zero is actual authored metadata. `FB490` returns item flags to **0D** before original `BA2A0` stores the parent/node links. `E9EC1` finally stores the selected current-hand byte. [CE510 selection](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/000ce510.asm), [E9D50](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/000e9d50.asm), [marker/transform owner](MP_WEAPON_ATTACHMENT_RESEARCH.md#link-transform-and-inventory-ordering).

Primary pickup holsters/detaches the old SMG but retains its slot 0 and owner; secondary pickup keeps both SMGs attached, with the new one first in the parent's child chain and sibling **00010002**. Neither case changes item ammo, zero heat or the shared RNG. BR stays **36/72** loaded/reserve; each SMG stays **60/120**. These are actual stored-state results, not constructor defaults supplied by this observer. [Final source states and ordered link stores](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/report.json), [attachment evidence](MP_WEAPON_ATTACHMENT_RESEARCH.md).

## Same-phase input marshalling

The source primary BR path leaves `150F00` with action flags **0001**, stale sequence **1** and selected slots `[0,FF]`. Its gameplay word becomes **10000000** under the original pressed-button handling at `151109/151110`; this output is retained even though the threshold interaction succeeded. `151C90` produces the actual `7C`-byte `C8140` input. At `C818F` its incoming sequence 1 differs from unit sequence 2, so the `C819B` selection-word store is skipped. Current/desired BR selection survives. Do not manufacture a pickup-only payload that discards the original remaining flags. [150F00](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/00150f00.asm), [C8140](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/000c8140.asm), [measured control bytes](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/report.json).

The secondary SMG path differs: `150F00` retains action flags **0070**, then its later inventory refresh produces payload sequence/slots **2 / `[0,1]`**. `C8140` takes the equal-sequence branch and writes the same correct inventory-selection word. The original refresh stores are source-listed at `151572/1515DA`; this extension measures the actual owning routine input/output buffers rather than adding a separate per-instruction payload-store probe. Primary stale-sequence rejection must not be generalized to secondary pickup. Player-owned consumption flags still prevent repeated held requests in the independent earlier continuous-input coverage. [Source refresh](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/instructions/00150f00.asm), [consumption contract](MP_PICKUP_CONTROLS_RESEARCH.md#player-admission-consumption-and-sequence-ownership), [measured primary/secondary C8140 inputs](../analysis/multiplayer/integration/inventory-source/pickup-transfer-measured/report.json).

## Remaining live producer chain

This extension can execute the control/action/owner/slot/unregister/attachment producers from original source-owned state without supplying success. Actual capability lookup uses the real equipped Spartan manager and resident graph bytes; item allocation, definition/ammo/heat/bounds and authored target datum already come from the original constructor/row producer. Current unit and weapon node matrices in this fixture are source-evaluated graph results. The existing explicit near-root input is preserved, and ordinary source terrain visibility runs against Lockout. The ordinary cases do not invoke the unavailable Havok shape service. [Allocated/equipped inputs](MP_PICKUP_EQUIPPED_RESEARCH.md), [actual current geometry](MP_PICKUP_VISIBILITY_RESEARCH.md), [FBFA0 point producer](MP_ITEM_POINT_RESEARCH.md).

Live integration still needs the original current player/item root, current animation/node phase, world membership, normal item tick/contact/settling state and engine-stage schedule. These snapshots are bounded stored-state transfer fixtures; they cannot replace those live producers with a guessed spawn offset, contact, hand matrix, gravity, friction or success return. Complete player/unit datum startup and Havok research remain separate work. Exact Xbox reciprocal results remain unresolved for the source-produced animated matrices. The direct-drop case also reaches the already declared unavailable Havok boundary once; its placement is not promoted to ordinary terrain or live settling proof. [World boundaries](MP_ITEM_WORLD_RESEARCH.md), [attachment reciprocal boundary](MP_WEAPON_ATTACHMENT_RESEARCH.md#frozen-results-and-numerical-boundary).

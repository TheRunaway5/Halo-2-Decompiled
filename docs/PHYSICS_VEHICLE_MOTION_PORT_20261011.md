# Vehicle state construction and motion port — 2026-10-11

The active players/vehicles/objects physics goal remains incomplete. This component adds 48 complete native routine bodies (8,019 original instructions) to the retained 32-body controller/object-update graph. The composed graph contains 80 bodies and 10,613 instructions, authenticated against the owned Map Pack 1.1 and English TU1.5 executables.

`source_run_physics_vehicle_motion_runtime` composes the prior update component with the original state constructor (`2095A0`), tank, wheeled, class-3, hover, flight and generic motion routines, the force/contact-processing body (`209A50`), original transform/marker queries, rigid-body inertia methods and math helpers. Every generated instruction becomes a compiled C++ operation, branch or native owner call. Production neither decodes opcodes nor executes the original binary. Unknown calls retain their reached ABI and require an actual owner; there are no successful stub returns or captured-result replays.

The three rigid-body virtual tables and their matrix/force method targets are authenticated through constructor-written image references in both executables. The generated code uses the selected image's addresses. New lowering covers FSIN/FCOS through real x87 instructions, signed FIMUL, FDIVP, REP stores, MOVHPS and CVTTSS2SI. The prior vehicle source cohorts, including the shared required-owner exception fix, remain unchanged. The shared checkout has an independently updated world implementation; it is preserved, excluded from this standalone vehicle library and checked separately through its root compatibility tests.

## Bounded original-execution evidence

The independent oracle executes untouched original instructions in Unicorn. It captures 3,957 cases per executable; 2,437 return completely and 1,520 stop at actual unported owners. Native comparison checks 2,779,263 instructions, 451,797 ordered writes and 1,400,600 retained bytes per image, plus GP/SSE state, active 80-bit x87 values, FS, defined integer flags and defined x87 status bits. Instruction and write order are checked, including repeat-string iterations and nested-owner failure prefixes.

All 576 standalone state-builder cases return completely. Another 432 cases execute the original builder, then call a motion routine using the state it computed. The native test runs the native builder first and passes its own computed state forward; it never installs the oracle's builder result. The only inter-call setup is the declared calling convention, with explicitly observed stack writes. Hover (81), flight (27) and generic (270) staged cases return completely. Tank (27) and wheeled (27) staged cases retain their actual CRT-remainder and solver-owner stops.

Inputs include 48 full vehicle tag records and their authored model/render-model metadata from Coagulation, Headlong and Zanzibar. Their source file offsets and hashes are retained and audited. Rigid-body/component/object records, 128 identity node poses, controls, animation fields and environment records are declared test inputs. The environment has session mode 4, a declared eight-float physics record `(1,0,0,0,0,0,0,0)` and no component constraints. These are bounded routine inputs, not source-created live vehicles or a measured game world. Definition overlays are recorded explicitly. Original state construction and marker processing run normally; no contact or callee output is inserted.

6,447 of 10,613 compiled instruction sites are exercised. The state constructor exercises 318/323 sites. The class bodies exercise tank 132/178, wheeled 162/248, hover 953/1,092, flight 941/1,179 and generic delivery 184/289 sites. The available authored definitions do not exercise class 3 (0/756); its full paired body is compiled but remains execution-unverified. The contact/force body exercises 301/1,452 sites, so collision-response parity is not established.

A first draft compared an unspecified x87 C2 value after arithmetic/FCOMIP and failed despite identical data, stores and control flow. The final contract derives its status mask from the executed instructions and [Intel SDM Volume 1, Table 8-1](https://www.intel.com/content/dam/support/us/en/documents/processors/pentium4/sb/25366521.pdf#page=220). TOP always remains checked; defined comparison bits and FSIN/FCOS range bits are checked when defined at the boundary. The failed log is retained. Native code was not changed to imitate an emulator's unspecified flag value. Exception flags, C1 and unmasked exception behavior remain outside this contract.

# Multiplayer render CPU measurements

The actual rebuilt multiplayer runtime improved, but full physical-monitor refresh has not been established. At the same 1280×720 drawable, median active frame time fell from 38.70 to 27.00 ms with one view and from 103.82 to 60.38 ms with four views. The remaining largest measured block is `Renderer::draw`; its current timing combines CPU preparation/encoding with fence, acquire and presentation waits. These measurements do **not** establish GPU execution time or physical-monitor refresh parity.

## Actual runtime evidence

Evidence directory: `analysis/multiplayer/integration/render-cpu-profile-20261008`. `runtime-summary.json` is generated by `tools/summarize_mp_render_cpu.py`. Each original/rebuilt run submits 210 frames, discards the first 30, then summarizes 180 complete submitted frames. All four timing files and logs are retained.

The probe uses the actual `run_multiplayer`, authored Lockout data, the user-owned authenticated u5 English executable, stock SMG starts, native local participants, original camera/admission/material/shader producers and the ordinary Vulkan renderer. It does not provide alternate simulation, poses or rendering results. The probe mutes audio and supplies no action input. No screenshot or per-vertex hashing runs during measured rendering. The read-only timing callback writes after the recorded active-frame interval; that interval also ends before final local-container destruction. Its inverse mean is therefore an **active-frame timing indication**, not a measured physical display refresh or GPU presentation timestamp.

Provider context: forced `SDL_VIDEODRIVER=x11`, an isolated Xvfb 1280×720×24 screen, runtime-selected **NVIDIA GeForce RTX 5080**, and a host **AMD Ryzen 7 9800X3D**. The test-only SDL controller whitelist admits VID/PID `0/0` and then asserts there are **zero recognized controllers**, including every input poll. It changes no physical controller or system configuration. A future physical device with those IDs would cause the probe to reject instead of silently contributing input. Team GPU runs were sequentially coordinated. No claim is made about physical monitor refresh, other maps, 16 participants, hardware outside this host, action-heavy PvP or GPU bottleneck attribution.

Median time in milliseconds; four-view phases sum the four actual view records:

| Phase | One before | One after | Four before | Four after |
|---|---:|---:|---:|---:|
| CPU preparation outside drawing | 14.93 | 4.81 | 58.14 | 17.46 |
| Static world construction/selection | 10.81 | 1.07 | 42.62 | 4.10 |
| Player body/held-SMG posing and selection | 0.00 | 0.00 | 5.83 | 3.67 |

The inverse mean active-frame indications are 25.74→36.40 per second for one view and 9.51→16.47 for four. The four-view timing counters retain **12 body draws**, while body builds change from **12 to 4**. The one-view probe has only one participant and consequently no other-player body draws; it must not be used to infer the cost of one camera observing a full roster.

The baseline executable is retained as `runtime-before-profile.bin`, SHA-256 `3176e6003bca69be624bae052e1efdf23140ca88b152db75054a25e7bc336880`. Baseline runtime/header snapshots and pre-change BSP source/header are retained with `baseline-pins.json`. Rebuilt runtime/renderer snapshots and final file hashes are listed in `manifest.json`.

## Source-preserving changes and comparisons

### Per-part stipple level

Before the change, `SourceBspShaderScene::select` called `source_shader_instance_stipple(alpha).level` for **each vertex with a selected part binding**. The existing helper builds all 32 rows of the 32×32 pattern, although this caller only reads its level. Alpha is already a fixed value of each selected authored part. The narrow production change stores the **same existing helper result** in that selected binding and copies its level to each vertex. It does not change alpha calculation, rounding, patterns, selected material, shader LOD, visibility, vertex order or shader programs.

Pre-change `src/source_bsp_shader_scene.cpp` SHA-256: `b643b3bc07bbf1a2da50e34812c7f6943b3d63134948f941f73f6e83c79884a7`. Changed SHA-256: `0ddba509b539a8c416b4463b63235040d78187aea7ae297c0ccba8f4c828c0bc`.

The isolated proposal and independently compiled actual production change each match:

- All **256 alpha values**, complete helper level and all **32 pattern rows**, across three repeated reads.
- **80** complete selected Lockout vertex buffers, including every field of each 132-byte `Vertex`, and complete ordered part records: geometry, section, part, shader LOD, material, coverage and instance alpha.
- Sixteen native-match states, one-view and four-view camera cells, original portal/fog admission and real authored BSP data. Each selection begins with **43,329** authored expanded vertices.

The isolated selection median was 9.676→0.355 ms. This excludes camera/admission construction, geometry copying, GPU work and other runtime phases; the actual runtime static-world result is reported separately above. The helper's source-backed existing arithmetic is reused without any new interpretation of retail code. The comparisons establish equivalence to the existing native selection implementation, not a new claim that all retail rendering owners are recovered.

`tools/prepare_mp_render_cpu_reference.py` verifies both retained pre-change native source hashes and regenerates the renamed comparison class. `tools/benchmark_mp_bsp_stipple_cache.cpp` compiles that class alongside the actual changed production source. `bsp-stipple-production.tsv` and its last selected full vertex fixture retain the independently repeated production comparison.

### Player body cache

The old per-view loop independently sampled body nodes, sampled/skinned the same body again, then reconstructed the same carried-SMG attachment and pose. For a given participant in one render frame, its source identity, root, idle graph/clip and chosen interpolation time do not depend on the observing camera. The root-owned runtime change lazily retains **undecorated** body/SMG vertices for that frame, uses `skin_model_world_nodes` on the already posed body bank, and copies geometry for each view before its own shader selection/material offset.

`tools/benchmark_mp_body_pose_cache.cpp` verifies **2,520** complete native body, 52-byte model-node and held-SMG output buffers across 84 native-match/fractional-frame inputs. Actual loaded models have **9,258 body vertices** and **2,070 SMG vertices**. Attachment marker selection, `compose_transform`, source attachment alignment/local conversion, child root composition and child pose retain their existing order and arithmetic. All compared bytes and output order match. This CPU-only comparison does not supply shader choices, lighting or GPU results.

Small isolated kernel timing was allocator/cache sensitive and did not justify a large standalone performance claim. The actual runtime improved body phase from 5.83 to 3.67 ms and confirmed 4 builds for 12 draws. One-view rendering retains its direct path; a redundant retained-copy cache made that kernel slower in an early proposal.

### Consecutive draw-key iterator cache

The root-owned renderer change retains the same `std::map` ordering and complete key `{material, lightmap, bsp_cluster, source_section, source_part}`. It only reuses the count/cursor iterator when the next vertex has that **exact** key. Every original material/lightmap bounds check remains. Sorting, counts, stable vertex scatter, source draw identities and descriptor request order are unchanged.

`tools/benchmark_mp_vertex_group_cache.cpp` uses the complete actual selected Lockout world fixture and checks **258** complete stable vertex/ordered draw-request comparisons. Additional explicitly controlled cases cover empty buffers, reversed triangle blocks, alternating distant part keys, repeated grouping into a nonempty destination and both bounds rejection branches. They are algorithm controls, not claimed naturally emitted gameplay cases. The CPU tool retains the exact ordered GPU descriptor request arguments; it does **not** fabricate or query Vulkan descriptor handles.

For 120 post-warmup CPU-only samples, one grouped world has 43,329 vertices/220 draw keys/220 key runs: median 1.350→0.658 ms. Four repeated groups have 173,316 vertices/880 keys/runs: 7.312→3.885 ms. The four inputs here repeat the same selected world for an isolated grouping-cost comparison; the actual four-view runtime still independently selects each camera's world.

## Cache boundaries

Safe retention is bounded to the **same render frame** and actual inputs. For a wider retained cache, the key must include complete participant/unit/weapon generation, model/permutation, graph/clip, source fractional frame, root transform/scale/reflection and attachment/IK inputs; rebinding, respawn, death, transform, clip or controller changes invalidate it. No such temporal cache is introduced here.

These inputs remain independently owned by each view:

- Camera, projection, split rectangle, scope observer and current frame interpolation.
- Portal/fog admission, world geometry/shader LOD and stipple alpha.
- Lighting query scheduling and each view's snapshot of the resulting bank. An earlier view's visit is not an original light-query deduplication event.
- Model shader collector coverage, shader LOD selection and mutable selected vertex/material copy.
- First-person source owner/hand binding, clip/channel/clock/frame, aiming/IK and camera composition. Full first-person world vertices cannot be shared just because the weapon model is the same.
- Sky/reflection eye, water frame/geometry, HUD state, scope mask and roster.

Material animation runs once in the existing common phase at its actual `shader_time`; ammo input remains assigned by each actual weapon material range. A cache keyed only by shader name would lose object colors, pass/implementation/LOD, owner inputs, ammunition and animated bitmap state. No such cache is proposed or installed. No shader programs, lighting effects, fog, water, HUD, resolution or quality were removed.

## Remaining frame-time seam

The renderer hardcodes `VK_PRESENT_MODE_FIFO_KHR`. It waits for the prior frame fence, acquires with an infinite timeout, submits the command buffer and presents through the ordinary queue. There is no newly added render cap or sleep in the successful ordinary render loop; the fixed 33,333 µs sleep belongs to the headless/network simulation provider. FIFO selection alone does not reveal actual display refresh, presentation intervals or which observed renderer cost is CPU versus GPU waiting.

The next useful read-only renderer timing boundaries are: prior-frame fence wait; material/animated resource preparation; per-view material/lighting/fog/water uniform construction; vertex grouping/scatter and uploads; swapchain acquire wait; command encoding; submit; and present. Driver calls can block, so their host wall time must remain labeled accordingly. GPU timestamps or genuine hardware presentation measurements would be separate evidence. The current combined 42.84 ms four-view renderer block cannot safely be attributed to shaders or GPU execution without that separation.

Read-only review of the newly instrumented renderer confirms clean boundaries after the fence, after global constants, after per-view postprocess/constants, after geometry/upload, after acquire, after command encoding, after submit and after present. Remaining **unmeasured** CPU candidates within the per-view constants loop are repeated `fog_material_passes.find(m)` lookups; repeated construction of the same immutable filtered `pixel_externs` mapping list; and repeated lighting-range scans for overlays sharing the same material root. Caching those resident lookups/lists could preserve the existing per-view program/constant operations. The lighting choice would need the actual ordered binding bank and retain first-match/range-validation semantics. No such changes are made or performance benefit claimed here.

## Reproduction

Use `tools/profile_mp_render_cpu.cpp` linked with the desired actual `multiplayer_runtime.cpp` object and matching build libraries. Its arguments are `MAP SHARED UPDATE_XBE VIEWS FRAMES WIDTH OUTPUT_TSV`; the measured commands use views 1 and 4, frames 210, width 1280, forced X11 and the isolated Xvfb screen above. The original supplied executable/map inputs remain user-owned; this work does not obtain new game payloads.

Run `tools/summarize_mp_render_cpu.py` against the evidence directory to regenerate the JSON summary. The retained native reference source and compiler commands/paths are recorded in `reproduction.json`; kernel comparisons use optimized C++20 with separate floating-point operations (`-fno-fast-math -ffp-contract=off -frounding-math`) where applicable. These tests verify the supported source-preserving transformations and the measured native paths; they do not establish complete multiplayer or campaign parity.

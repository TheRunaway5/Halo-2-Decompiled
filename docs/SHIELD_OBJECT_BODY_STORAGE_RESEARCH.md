# Persistent original object body storage

Research snapshot: 2026-10-11. The narrow next owner is a **persistent finite body heap attached to the existing shared object-header bank**, reusing the complete `BD170` allocation and `BD270` append owners. Both native direct owners and the underlying original heap algorithms already exist. The adapter must retain allocation state and raw bytes, expose real relocation, and retire each shared header once. This supplies storage; it does not produce complete construction flags, pose, physics, registration or shield collector admission. The next state-production boundary remains the actual generic constructor and its required services described in [the registration packet note](SHIELD_REGISTRATION_PACKET_PRODUCERS.md).

This research changed no implementation or tests. ## Complete allocation and append contracts

**BD170:** `16D2C0` first reserves a header from the shared pool. Its `NONE` result returns immediately without a heap attempt. Header address is `pool+44 + 12*low16(datum)`. `BD187` sign-extends the caller's extent short; `BD19F` pushes metadata0, `BD1A2` selects the stable output cell `&header+8`, and `BD1A6` sets the other metadata argument `EAX=0` before `18FCE0`. Thus **both heap metadata arguments are zero**. On heap failure it reloads the shared pool and retires this header through `16D4C0`, returning `NONE`; it never writes extent`+6`. On success `BD1B6` writes the caller's low16 extent, followed by exact base-range zeroing: dwords at`BD1C6`, tail bytes at`BD1CD`. The raw heap itself does not zero payload. [Complete instructions](../analysis/damage-shields-goal-20261011/overlay-pass/registration/body-storage/paired/instructions/000bd170-old.asm), [existing complete native kernel](../src/unit_action_dispatch.cpp#L56).

**BD270 zero request:** reads the signed descriptor offset and current body pointer, writes descriptor offset`+2=FFFF` at`BD2A8`, then descriptor size`=0` at`BD2AE`, returns AL1, and performs no heap grow. Preserve this store order. [Complete instructions](../analysis/damage-shields-goal-20261011/overlay-pass/registration/body-storage/paired/instructions/000bd270-old.asm).

**BD270 nonzero request:** x86 shift semantics yield `mask=(1u<<(alignment&31))-1`; padded extra is `signextend16(size)+mask` with32-bit wrap. New heap request is `signextend16(header+6)+extra`, again wrapping32 bits. `EAX` carries that request; `EBX=&header+8`; `BD2D7/BD2DA` push both metadata arguments0, and `BD2E3` pushes the heap before `18FD70`. A false grow returns AL0 without BD270's extent, descriptor or zeroing stores. The heap may relocate body storage but **must leave header extent`+6` unchanged for BD270 to consume**. [Instructions](../analysis/damage-shields-goal-20261011/overlay-pass/registration/body-storage/paired/instructions/000bd270-old.asm), [existing native append owner](../src/unit_constructors.cpp#L250).

After grow succeeds, `BD2F5` zero-extends the old extent word; `BD2FC` commits low16`(old+extra)` to header`+6`. It re-resolves the current pool/body pointer and signed descriptor offset, writes low16`((old+mask)&~mask)` to descriptor`+2` at`BD317`, then writes the original raw size word at`BD320`. It finally zeroes the **entire padded extra range** from relocated body plus **sign-extended old extent**, using dword stores`BD333` then tail-byte stores`BD33A`. Descriptor writes precede zeroing, even when an adversarial overlap would erase them. No descriptor content or padding is synthesized ahead of these instructions. [Complete append instructions](../analysis/damage-shields-goal-20261011/overlay-pass/registration/body-storage/paired/instructions/000bd270-old.asm).

The native `UnitConstructorObjectPool.body(index)` service must expose actual enlarged **physical backing immediately after grow**, while the old logical extent is still in header`+6`. Returning only a logical-size subspan fails the existing append owner's post-grow bounds checks. Callers reacquire the body after relocation; retaining a former body span across grow is invalid. The declared bounds checks reject unsupported negative/wrapped spans; in particular the native base owner hard-stops a negative extent that a malformed raw heap admitted, rather than inventing an original `NONE` result. The13 actual selected base extents avoid that malformed branch. [Pool/append contract](../include/halo2/unit_constructors.hpp), [native base checks](../src/unit_action_dispatch.cpp#L56), [native append checks](../src/unit_constructors.cpp#L250).

## Real heap outcomes and release

The recovered heap is composable without caller-supplied success booleans. `18FCE0` computes a16-byte-aligned physical block size from wrapped requested bytes plus `10h` overhead (`20h` with debug enabled). With gap-search`+3D` enabled it tries `1900C0` then `190030`; its ordinary/fallback append is `18FF90`. All use the retained finite arena and linked blocks; no fitting block returns AL0 without changing the output pointer. Successful block header fields are size`+0`, owner pointer-cell token`+4` (zero when heap`+3C` disables tracking), next`+8`, previous`+C`, followed by payload at`+10`. [Allocation](../analysis/damage-shields-goal-20261011/overlay-pass/registration/body-storage/heap-instructions/0018fce0-old.asm), [native heap](../src/object_body_heap.cpp#L103).

`18FD70` extends in place only if the new physical endpoint fits before the next block or arena end; it updates size/free accounting. Otherwise it really allocates into a private scratch pointer cell. Failed relocation allocation returns AL0 with the old allocation intact. Success copies the **old physical payload extent**, `old_block_size-(debug?20h:10h)`, using dwords/tail bytes, frees the old block, rewrites the new block's owner cell to the original `&header+8` token (or zero when tracking disabled), then publishes the new pointer there. It does not clear newly added bytes or commit header`+6`. Scratch must be a separate genuinely owned region, never a header/body alias. [Complete resize](../analysis/damage-shields-goal-20261011/overlay-pass/registration/body-storage/heap-instructions/0018fd70-old.asm), [frame contract](../include/halo2/object_body_heap.hpp#L12).

`BD1F0` first reads body`header+8`, then clears header flags`+2` at`BD215`. For a nonzero body it restores the physical block size to heap`+30` at`BD225`, splices previous/next links or updates heap endpoints, and only then clears header body pointer`+8` at`BD250`. It reloads the shared pool and invokes `16D4C0` at`BD25C` **afterward**. It does not clear header type`+3` or extent`+6`; the retirement leaf owns bitmap/salt/count/free-search changes and optional debug fill. Raw heap `18FE60` alone neither clears the output pointer cell nor retires the datum. [Complete storage release](../analysis/damage-shields-goal-20261011/overlay-pass/registration/body-storage/paired/instructions/000bd1f0-old.asm), [header retirement](../analysis/damage-shields-goal-20261011/overlay-pass/registration/body-storage/paired/instructions/0016d4c0-old.asm), [native full release](../src/object_storage_release.cpp#L49), [raw heap free](../include/halo2/object_body_heap.hpp#L33).

The current complete storage-release owner includes raw header retirement. Do not run it and then independently retire the same shared datum again through `NativeObjectLifetimes`. A persistent adapter may compose equivalent body-free/flags/pointer stores with **one** shared-header retirement, retaining source order and a native lifetime bookkeeping event. General object destruction, attached-object teardown and unregister are earlier distinct owners; this storage leaf is not their replacement. [Release implementation](../src/object_storage_release.cpp), [shared lifetime contract](../include/halo2/native_object_lifetimes.hpp), [lifetime handoff](SHIELD_OBJECT_REGISTRY_RESEARCH.md).

## Early native type byte and persistent ownership

The inspected `NativeObjectLifetimes::reserve(type)` immediately wrote header`+3` after reservation. Original `16D2C0` zeroes the whole newly reserved12-byte header before restoring its salt. `BD170`, `BD270`, the recovered raw heap and `16D4C0` do not read header type`+3`, so the extra early store does not change their consumed allocation size, branch, pressure or relocation decisions for identical well-formed backing. It **does** change raw bytes and store chronology: actual generic construction writes this type only at`B8B0B`, after successful BD170. With debug fill disabled, failed-body retirement clears salt/bitmap but can retain the early type byte in the dead slot until its next reservation clears it. Therefore allocator-result equivalence cannot be labelled complete header/store equality. [Original reservation](../analysis/damage-shields-goal-20261011/overlay-pass/registration/body-storage/paired/instructions/0016d2c0-old.asm), [retirement](../analysis/damage-shields-goal-20261011/overlay-pass/registration/body-storage/paired/instructions/0016d4c0-old.asm), [frozen native reservation](../analysis/damage-shields-goal-20261011/overlay-pass/registration/body-storage/native-snapshot/src/native_object_lifetimes.cpp#L14), [generic type store](../src/object_construction.cpp#L90).

The parent's concurrent implementation now introduces `reserve_storage()` with an untyped `FF` **sidecar** marker and a genuine zero header type byte, leaving the original generic constructor to write header`+3`. This direction resolves the chronology problem; it is implementation status, not a new original-execution result from this research. [Current lifetime interface](../include/halo2/native_object_lifetimes.hpp#L30).

The minimum adapter owns one retained arena, immutable selected type extents/name input, private resize scratch and stable opaque32-bit tokens for each actual shared `header+8` cell. The address resolver must map these tokens directly to the **same shared header bank**, never a copied bank or second datum allocator. Body spans resolve through the current header pointer and physical block extent. `SourceRuntimeMemory` already supplies owned token-addressed regions and stable views across mounting other regions; its copy operations are deleted, so checkpoint support requires an explicit complete snapshot/clone strategy. Restoring only `NativeObjectLifetimes` would leave heap links, body bytes and pointer-cell tokens inconsistent. [Memory contract](../include/halo2/source_runtime_memory.hpp), [frozen shared pool](../analysis/damage-shields-goal-20261011/overlay-pass/registration/body-storage/native-snapshot/include/halo2/native_object_lifetimes.hpp), [heap services](../include/halo2/object_body_heap.hpp).

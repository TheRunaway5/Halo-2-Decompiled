## Remaining seams, with admission boundaries

1. **A second core for completed presentation jobs.** After original source preparation has produced an owned WORLD-node/geometry/section snapshot, independent model skins or substantial CPU-only packet planning can run on a worker and join at their original ordered consumer. Retain full owner generation, model/LOD, immutable geometry, complete current WORLD nodes, view inputs and result lifetime. Keep mutable frame-cache maps/counters and renderer calls on their owner, or give jobs disjoint storage. This is a candidate refactor, not an existing admitted worker path. Running the same float kernel on another thread is insufficient proof: FP controls/status, errno, diagnostics, allocation failures and observer/error ordering need explicit admission/fallback and direct comparison. Simple packing is easier to isolate, but its saved work must exceed scheduling and any added copy cost.

2. **GPU ordinary base-model processing using original declarations/programs.** Keep animation, gameplay/attachment/bounds node banks and original source callbacks on the CPU. Transfer the completed palette and retain raw authored vertices/indices; extend the existing raw bridge to ordinary base materials. The current packed ordinary adapter accepts only class 0 ([declaration:31](/home/eric/Developer/Halo-2-Decompiled/src/rendering/source_vertex_declaration.cpp:31)); substituting a skinned program without its original weights/indices/declaration is invalid. Required proof includes exact selected LOD/section order, palette remaps/compounds, original influence arithmetic, PRT/lighting/material/override/fog passes and actual output. Modern shader float behavior is not automatically the CPU or NV2A contract; Vulkan exposes explicit controls for rounding/denormals/signed-zero/Inf/NaN, whose supported modes still need qualification. [Khronos float controls](https://github.com/KhronosGroup/Vulkan-Docs/blob/main/appendices/VK_KHR_shader_float_controls.adoc). No blanket GPU-skinning gain or parity claim is justified.

3. **Parallel command recording after immutable draw plans are complete.** Partition substantial independent ordered ranges into a small number of worker-owned command buffers, then execute them in the original order. Keep queue submission/present and resource publication serialized; prewarm/freeze shared lazy pipeline maps or isolate them. The existing raw `prepare()` mutates descriptor/pipeline/frame storage ([native draw:436](/home/eric/Developer/Halo-2-Decompiled/src/ui/menu_world_native_draw.cpp:436)), so invoking it concurrently is not safe as-is. Vulkan requires external synchronization of each command pool, including recording through its buffers; separate worker pools and descriptor allocation ownership are required. [Khronos threading](https://docs.vulkan.org/guide/latest/threading.html). Secondary-buffer inheritance, pass state and workload size also matter; excessive small secondary buffers can regress performance. [Khronos sample](https://docs.vulkan.org/samples/latest/samples/performance/command_buffer_usage/README.html). Moving command encoding alone does not remove the larger source-owner work.

A smaller presentation-only candidate is the radar compositor: [HUD:806](/home/eric/Developer/Halo-2-Decompiled/src/ui/hud/multiplayer_hud.cpp:806) updates history and builds a plan; [814](/home/eric/Developer/Halo-2-Decompiled/src/ui/hud/multiplayer_hud.cpp:814) rasterizes it. Leave history/visibility/tick ownership ordered and pass an immutable plan/artwork/color bank to a worker or future GPU compositor. Preserve exact sampling/mips, clipping, blending, output bytes and FP obligations. Current CPU sampler/pointer hoisting is already implemented; worker/GPU migration remains unmeasured.

The hard boundary is visible in [source_model_build:43](/home/eric/Developer/Halo-2-Decompiled/src/rendering/models/source_model_build.cpp:43): shared scratch, view/frame cache acquisitions, arena cursor/context writes, node-bank construction, rebase/PRT/lighting callbacks and color refresh all occur in source order. [runtime:4737](/home/eric/Developer/Halo-2-Decompiled/src/gameplay/multiplayer/multiplayer_runtime.cpp:4737) performs this work inside the actual model world; [4758](/home/eric/Developer/Halo-2-Decompiled/src/gameplay/multiplayer/multiplayer_runtime.cpp:4758) copies completed owners/poses/section order. Running views, visibility or shadow writers simultaneously against that mutable world could change the next source read and gameplay-visible observers. A mutex around everything preserves serialization but supplies no parallel speedup. A completed packet/snapshot boundary is the useful seam.

GPU writes/descriptor reuse must also remain behind the existing fence; host-visible mapping alone supplies no synchronization. Vulkan makes the application responsible for resource synchronization. [Khronos synchronization](https://docs.vulkan.org/guide/latest/synchronization.html). None of these options requires reducing simulation frequency, changing physics, source LOD/visibility, resolution or visual effects.

## MCC: confirmed mechanisms, not an exact live performance explanation

The retained [binary evidence](/home/eric/Developer/Halo-2-Decompiled/build/test-results/mcc-classic-performance-reference-20261022/binary-evidence.json) pins MCC `halo2.dll` version 1.3528.0.0, AMD64, SHA-256 `de65b4f4fdbf3f0a5eab7431fe530da17dd815599182dfd6ae9b7e21cf171946`. This audit reads that evidence; it neither re-executes MCC nor silently treats the installed file as newly rehashed.

| Indexed instancing branch | `DrawIndexed` at `0x180107c90`, conditional `DrawIndexedInstanced` at `0x180107ca8`. Producer grouping and live instance counts are unknown. |
| Retained native buffers | Three-buffer allocator/upload rotation at `0x18010fc80..0x18010ffb2`; immutable/default buffer creation at `0x180110090..0x18011010b`. Rotation cadence, frames in flight and which meshes use each allocator are unknown. |

Microsoft confirms deferred contexts can record on separate threads while immediate playback remains serialized; an individual context cannot be used concurrently. These are API rules, not proof MCC uses all available parallelism. [Rendering](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-render-multi-thread-render), [thread ownership](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-render-multi-thread-intro). `ExecuteCommandList` can merge onto another deferred context, but eventual GPU execution requires the immediate context; the shared native field offset alone does not identify which instance executes a list. [Microsoft method contract](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-executecommandlist).

There is still **no verified live MCC Classic worker schedule, per-family GPU-skinning placement, GPU culling/indirect architecture, pass timing or matched MCC/port comparison**. Consequently we can identify concrete architectural differences and optimization directions, but cannot truthfully assign the reported 4K120 result to one exact mechanism. Native execution efficiency is the strongest demonstrated comparison; the fraction of the FPS gap attributable to it remains unmeasured. Earlier source-runtime/profile percentages belong to their pinned earlier executables and are not promises of current offload gains.
